# gettool 自动构建流程改造计划

## 背景

`cpp_tools` 已经具备工具库雏形：每个 buildable 工具有独立目录、CMake 配置、pybind11 入口和示例；`pywayne` 侧包装类在导入失败时调用 `gettool` 自动拉取和编译。但这条链路仍依赖很多隐含约定，换一台 macOS 或 Linux 机器时，失败点可能出现在 `gettool` 不在 PATH、依赖缺失、CMake 找不到 pybind11、产物没有复制到目标目录，或编译出的模块无法被当前 Python import。

这份计划关注近期改造，不处理算法功能本身。

## 核心问题

当前最大问题不是“能不能编译”，而是“失败是否可预测、可恢复、可解释”。现有实现已经能在熟悉环境里工作，但要做到开箱即用，需要把工具元数据、构建过程、Python 导入验证和包装类自动安装抽成统一协议。

## 目标

- `gettool <tool> -b -t <lib_path>` 在 macOS/Linux 上能完成源码获取、CMake 构建、产物复制、运行时依赖打包和 import 验证；依赖预检仍需继续细化。
- `pywayne` 包装类不再各自复制 `_check_and_import_lib()`，而是调用公共 `pywayne.cpp_loader.import_cpp_module()`。
- `name_to_path_map.yaml` 成为工具注册表，而不是只有路径和布尔值的半结构配置。
- README、roadmap、CI 和实际命令保持一致。

## 范围

本计划覆盖：

- `cpp_tools/name_to_path_map.yaml`
- `wayne_algorithm_lib/bin/gettool.py`
- `wayne_algorithm_lib/pywayne/*` 中调用 `gettool` 的包装类
- `cpp_tools/.github/workflows/build-tools.yml`
- `cpp_tools/README.md` 和 `docs/`

本计划暂不覆盖：

- 算法接口重构
- Windows 完整支持
- 发布二进制 wheel
- Pangolin GUI 运行态自动测试

## 方案

第一步不要急着做二进制分发。先把源码构建链路变成一个稳定协议：

1. 扩展工具注册表，显式记录工具的 Python 模块名、构建产物、依赖和平台能力。
2. 改造 `gettool.py`，把 build 拆成 fetch、preflight、configure、compile、copy、verify 六步，每一步有明确错误。
3. 在 `pywayne` 新增公共安装 helper，包装类只声明 tool/module/lib_dir。
4. CI 对所有 buildable 工具执行 build + import，不再只上传 `lib/`。
5. 等源码构建稳定后，再评估 GitHub Release 二进制缓存。

## 执行路径

| 阶段 | 目标 | 产出 | 判断标准 |
|---|---|---|---|
| P0 文档校准 | 把当前真实状态写清楚 | README 更新、roadmap、plan | 新读者能理解本仓库为何同时服务 C++ 和 Python |
| P1 元数据 schema | 让工具注册表能驱动自动化 | 新版 `name_to_path_map.yaml` 示例和校验脚本 | 每个 buildable 工具有 `path/python_module/artifact_glob/dependencies/platforms` |
| P2 gettool 构建协议 | 构建失败可诊断 | `gettool.py` 分阶段日志、依赖预检、产物验证 | 已完成当前 Python、CMake build、copy/import 验证和运行时依赖打包；依赖预检待补 |
| P3 pywayne helper | 自动安装逻辑收口 | 公共 `import_cpp_module` 和包装类迁移 | 已完成 4 个包装类迁移 |

| P5 二进制缓存评估 | 减少重复编译成本 | 产物命名规范、索引格式、回退策略 | `gettool` 能判断是否存在匹配平台和 Python ABI 的产物 |

## 风险

- `gettool.py` 不在本仓库，改造时需要同步修改 `wayne_algorithm_lib`。如果只改 README 或 YAML，实际自动安装仍会停在旧行为。
- 当前 CI 安装的是全量依赖，不能证明用户机器上的依赖预检足够好。需要设计更接近干净环境的验证。
- `generate_name_to_path_map.py` 会破坏当前对象格式 YAML，必须先废弃、修复或替换。
- Pangolin 依赖 GUI/OpenGL，上云环境只能验证 build/import，运行态要单独标注。

## 检查点

- `python cmake/cmake_manager.py check` 仍显示所有 pybind11 项目使用自包含配置。
- `gettool butterworth_filter -b -t /tmp/cpp_tools_test_lib` 后，当前 Python 能 import `butterworth_filter`。
- `gettool apriltag_detection -b -t /tmp/cpp_tools_test_lib` 缺依赖时能输出明确的系统包建议。
- `pywayne.cv.apriltag_detector.ApriltagCornerDetector()` 在空 `lib/` 目录下只调用公共 helper，并支持 `tag_family` 与可选预处理。
- CI matrix 包含 `dsp/butterworth_filter`，并对上传前产物做 import 验证。

## 下一步

下一步建议补 P1/P2 的剩余部分：把 `artifact_glob`、`system_dependencies`、`python_dependencies`、`platforms` 做成可校验 schema，并先用 `butterworth_filter`、`sliding_window_dsp`、`apriltag_detection` 在 macOS/Ubuntu CI 上跑 build + import 闭环。
