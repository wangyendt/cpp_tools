# cpp_tools 开箱即用构建路线图

## 当前状态

`cpp_tools` 已经形成了双用途工具仓库：工具目录包含 C++ 源码、`CMakeLists.txt`、pybind11 绑定和 `example.py`，可以被 `gettool` sparse checkout 后复制源码，也可以编译成 Python 扩展模块。`wayne_algorithm_lib` 侧的 `pywayne` 包装类通过公共 helper 在导入失败时调用 `gettool <tool> -b -t <lib_path>`，把编译产物放到当前 Python 包的 `lib/` 下。

本次检查确认了几个事实：

- `cmake/cmake_manager.py check` 检测到 6 个 pybind11 工具都已经使用自包含 CMake 配置。
- `name_to_path_map.yaml` 已开始记录 buildable 工具的 `python_module`、`bundle_runtime_dependencies` 和 OpenCV 组件，但系统依赖、Python 依赖、构建产物 glob 和平台限制仍未完整 schema 化。
- `README.md` 原先把 YAML 写成简单 `name: path`，也把 Windows 和“完全自包含”描述得过满，已经更新为当前真实状态。
- `gettool.py` 已改为使用当前 Python 解释器、`cmake --build`、构建后 import 验证，并在 macOS/Linux 上复制必要的非系统运行时依赖。
- `apriltag_detector`、`camera_model`、`pangolin_utils`、`logcat_reader` 已迁移到公共 `pywayne.cpp_loader.import_cpp_module()`。
- GitHub Actions 覆盖 macOS/Ubuntu 和多个 Python 版本，但工具矩阵没有包含 `dsp/butterworth_filter`，也没有把构建产物整理成 `gettool` 可选择的二进制索引。

## 背景与方向

这个项目的价值不只是存放 C++ 代码，而是把“需要 C++ 性能或系统能力的模块”变成 Python 侧可以直接 import、C++ 侧可以直接 include 的工具供应链。真正的开箱即用应该满足两类用户：

- Python 用户只写 `from pywayne.xxx import Xxx`，缺失本地扩展库时自动完成依赖检查、下载、编译、导入。
- C++ 用户只写 `gettool <tool> -c` 或等价命令，就能得到稳定的源码、头文件清单、依赖说明和 CMake 接入方式。

当前链路已经跑通了核心动作，但可迁移性主要依赖机器上碰巧具备 CMake、pybind11、OpenCV、Eigen、Boost、Ceres、Pangolin 等依赖。路线图的方向是把这些隐含前提显式化、自动化、可诊断化。

## 目标状态

目标状态不是把所有依赖都盲目源码编译，而是在 macOS 和 Linux 上提供一条确定的决策链：

1. 优先复用当前 Python 环境、系统包管理器和已有 CMake package。
2. 找不到依赖时给出准确安装建议，必要时才调用 `install_scripts/` 源码构建。
3. 构建完成后验证 Python 模块是否能从目标 `lib/` import。
4. C++ 模式输出 include manifest，让调用方知道需要哪些头文件、源文件和链接依赖。
5. CI 对每个工具、每个平台、每个 Python ABI 的结果可追踪，失败能定位到依赖、配置、编译或导入阶段。

## 里程碑

| 阶段 | 目标 | 关键工作 | 判断标准 |
|---|---|---|---|
| M1 元数据收敛 | 工具能力从代码约定变为可读配置 | 扩展 `name_to_path_map.yaml`，加入 `python_module`、`artifact_glob`、`system_dependencies`、`python_dependencies`、`cpp_manifest`、`platforms` | `gettool -l` 能显示工具用途、构建能力、依赖和平台限制 |
| M2 构建入口稳定 | `gettool -b` 在干净 macOS/Linux 上可诊断 | 依赖预检、CMake 参数注入、构建缓存、产物验证、错误分类 | 已完成当前 Python、CMake build、copy/import 验证和运行时依赖打包；依赖预检待补 |
| M3 Python 包装统一 | `pywayne` 侧不再复制粘贴安装逻辑 | 公共 `import_cpp_module(tool_name, module_name, lib_dir)` | 已迁移 `apriltag_detector`、`camera_model`、`pangolin_utils`、`logcat_reader` |
| M4 C++ include 模式可用 | `gettool -c` 不只是复制文件 | 为每个工具输出 include/source/link manifest，必要时生成小型 CMake include 文件 | 新 C++ 项目能按 manifest 接入 `butterworth_filter` 和 `sliding_window_dsp` |
| M5 CI 与二进制缓存 | 重复用户无需每次源码编译 | CI 覆盖所有 buildable 工具，发布按平台/Python ABI 命名的产物索引 | `gettool` 能优先下载匹配二进制，失败再本地编译 |

## 优先级

近期优先级应该放在 M1 到 M3。原因是当前最大风险不是某个算法实现，而是同一套流程在新机器上的失败不可预测：缺依赖、找错 Python、编译成功但 import 失败、包装类重复逻辑不一致。先把元数据、构建入口和 Python helper 打稳，后续二进制缓存才有可靠基础。

`butterworth_filter` 和 `sliding_window_dsp` 应作为第一批验收工具，因为依赖少，适合验证工具链本身。`apriltag_detection` 和 `camera_models` 应作为第二批，因为它们能暴露 OpenCV、Eigen、Boost、Ceres 这类依赖问题。`pangolin_viewer` 放在第三批，因为它涉及 GUI/OpenGL/headless 环境，应该单独标注平台限制。

## 依赖与风险

- `gettool` 目前位于 `wayne_algorithm_lib/bin/`，而不是本仓库内。两边的配置 schema 必须同步演进，否则 README 和实际命令会继续漂移。
- 当前 `generate_name_to_path_map.py` 会按旧的简单映射重写 YAML，不适合继续作为正式配置生成入口。
- OpenCV、Ceres、Pangolin 等依赖源码编译成本高，默认自动源码安装会让“开箱即用”变成不可控的长任务。
- Python ABI 与编译产物绑定，缓存或 release 产物必须包含平台、架构、Python 版本和工具版本。
- GUI 类工具在 CI 和服务器上可能无法运行完整示例，需要区分 build test、import test 和 runtime test。

## 未决问题

- `gettool` 是否应该迁入 `cpp_tools` 仓库，还是继续作为 `wayne_algorithm_lib` 的外部入口。
- 是否需要支持 Windows。如果要支持，CMake、依赖安装、动态库后缀和 CI 都需要单独规划。
- 二进制产物是放 GitHub Release、私有对象存储，还是继续只做本地编译。
- C++ include 模式是输出 manifest，还是生成可被调用方 `include()` 的 CMake package。
